# SQLite Migration Backend\n\nFastAPI service that upgrades existing SQLite application databases by\napplying versioned migration manifests over HTTP. Clients reference\ndatabases by **alias** only; file paths stay server-side.\n\n## Layout\n\n- `app/config.py` — alias -> db-file mapping, request limits, migration table name\n- `app/sqlsplit.py` — tokenising SQL splitter (strings, quoted identifiers,\n  line/block comments, `CREATE TRIGGER ... BEGIN ... END;` bodies)\n- `app/engine.py` — manifest validation, authorizer-based execution guard,\n  single-transaction apply, version/hash storage, per-db locking\n- `app/main.py` — HTTP API, request-size limit, error mapping\n- `make_example_db.py` — creates the example `shop` database (`data/shop.db`)\n- `demo.sh` — curl walkthrough: upgrade, idempotent resubmit, rollback\n- `tests/` — pytest suite (12 tests)\n\n## How it works\n\n- A manifest lists **all** migrations from version 1 (contiguous, positive,\n  no duplicates, non-blank SQL). `expected_version` must equal the last\n  manifest version.\n- Applied history is stored in `_schema_migrations(version, description,\n  sha256, applied_at)`; `sha256` is over the UTF-8 bytes of the original SQL.\n  On each request the manifest prefix must reproduce the applied history\n  exactly — altered or missing entries are rejected with 409. Only the\n  unapplied suffix runs; resubmitting an identical manifest succeeds without\n  re-executing anything.\n- The whole suffix (schema + data + migration rows) commits in **one\n  transaction** (`BEGIN IMMEDIATE`). Any error rolls everything back and the\n  response names the failed version and reason.\n- Statements are split by a real tokenizer, so semicolons inside strings,\n  comments and trigger bodies are handled. Each statement's leading keyword\n  must be one of CREATE/DROP/ALTER/INSERT/UPDATE/DELETE/REPLACE.\n- Execution is additionally guarded by a SQLite **authorizer** (not keyword\n  search): PRAGMA, ATTACH/DETACH, transaction control and any write to\n  `_schema_migrations` are denied — including writes fired indirectly by\n  triggers. Foreign keys are enabled and `PRAGMA foreign_key_check` must be\n  clean before commit, otherwise the batch rolls back.\n- Version check and execution hold a per-alias lock plus the SQLite write\n  lock, so concurrent submissions cannot double-apply or slip past the\n  expected version; contention returns 409. State is read from the database\n  on every request, so restarts are safe. Connections are closed after each\n  request. Requests are limited to 1 MiB / 200 migrations.\n\n## API\n\n- `GET /aliases` — list known aliases\n- `GET /db/{alias}/version` — current version + applied history with hashes\n- `POST /db/{alias}/migrate` — body:\n  `{"expected_version": N, "migrations": [{"version": 1, "description": "...", "sql": "..."}, ...]}`\n\nSuccess: `{"ok": true, "applied_now": [...], "current_version": N}`.\nFailure: `{"ok": false, "error": "...", "failed_version": V}` with HTTP\n400 (validation/SQL error) or 409 (history/expected-version conflict, busy).\n\n## Run\n\n```bash\n.venv/bin/python make_example_db.py          # create example shop.db\n.venv/bin/python -m uvicorn app.main:app --port 8141\n./demo.sh                                    # curl demo in another shell\n.venv/bin/python -m pytest tests/ -q         # test suite\n```\n\n## Scope / limitations\n\n- SQLite only; statement-level keyword allow-list; no SELECT in scripts.\n- Migration SQL runs as the service's OS user with full file access to the\n  mapped databases — protect the HTTP endpoint at the deployment level.\n- `expected_version` is validated against the manifest, and history is\n  hash-checked, so stale clients fail safely with 409.\n
